# SoP simulator update to MRL #146 as of 2026-10-20: design

Status: owner approved R1-R4 as recommended, 2026-10-21. Nothing here is
built. Plan: `docs/superpowers/plans/2026-10-21-sop-rev20261020.md`.

## Why

Our build (`patches/monero-sim-pop.patch`, log v3) and the oracle
(`scripts/sop_oracle.py`) implement the issue text of 2026-10-15. The text has
changed since, in two ways that matter for every cell we run:

1. **2026-10-16 22:07 (window).** The fork is judged subjectively only while
   `n_max < (k-1)*w` = 32, where `n_max` is the larger of the two branches'
   work-object counts **above h_f+1**: the first block after the fork (header
   and shares) is not counted, and neither are pool shares. We still use
   `max(n_main, n_alt) < k*w` = 48 with the first block counted
   (`under_kw`, patch line ~1097; oracle `decide()`). The 2026-10-16 conformance
   update missed this edit.
2. **2026-10-20 (tip shares).** A chain's score includes the valid workshares
   in the pool that extend its tip (`prev_id` = chain tip), at `diff/w` each,
   **under `sop_objective` only** (0 under subjective and nakamoto). Nodes
   also accept, without relaying, "alternate workshares" on the tip of a known
   alternate chain whose fork point is fewer than `10*w` blocks deep. We count
   a share only once a block carries it.

Also since 2026-10-15, with little or no effect on our runs: the fork choice
is defined over a set of candidate chains with iterative elimination
(10-16 17:50); a fork whose highest tip is `10*w` or more blocks past h_f is
scored `nakamoto` (plain difficulty); blocks with missing or invalid share
data are valid and count as 0 shares (we already do this); at most 200 shares
per block.

Race model estimate (`scripts/sop_race_model.py` `simulate()` with
`SimConfig.either_window` for the 10-16 edit and `count_honest_pending` added
for the 10-20 edit; 500 days, seed 1; attacker share of blocks). The 10-20 column gives the attacker no credit for its own
tip shares and has no delay, so it is biased against the attacker:

| alpha, give-up | as run (10-15) | + 10-16 window | + 10-20 tip shares |
|---|---|---|---|
| 1/3, d2, as built | 0.023 | 0.037 | 0.0004 |
| 0.40, d2, honest shares | 0.187 | 0.208 | 0.020 |
| 0.45, d5, honest shares | 0.425 | 0.442 | 0.066 |

So the results we have describe a rule the author has replaced, and the
remaining queue (stopped 2026-10-21 16:00Z) would have measured it again.

## Goal

A build, oracle, attacker and race model that follow the current text, so
the next campaign measures the rule as proposed today. Old results stay
reproducible from git (the v3 patch is committed), as with the v3 switch.

## Decisions for the owner (recommendation first)

- **R1. Replace the rule, don't add a flag.** As with v3 ("the revision with
  nothing optional"): one rule, the current text. A flag (`--sim-sop-rule`)
  would allow daemon A/B runs of each edit, but doubles the oracle and test
  surface, and the race model already separates the edits. Alternative: a
  single `--sim-sop-tip-shares off` switch for one ablation run.
- **R2. Pool shares count one per slot, contiguous from `major_version`.**
  The text admits pool shares whose `minor_version` "follows the
  sequentiality rule" but does not say what happens when two miners find a
  share for the same slot (they do, with two honest miners racing). Counting
  every pool share would let a chain's tip score exceed what any block could
  carry. Default: slot `V+i` counts if slots `V..V+i-1` count, first-seen
  wins per slot. The log carries every pool share, so the oracle and a probe
  can recompute the "count all" reading. This is a question for the thread
  once we have a reproduction.
- **R3. Re-evaluate only on block arrival.** monerod runs the fork choice
  when an alt block arrives; under the 10-20 text a share arriving can change
  which chain scores higher. Re-running the fork choice from the share
  handler (and reorganizing on a share) is a large change to monerod. First
  build: block arrival only, and a log-replay probe counts how often a share
  arrival would have flipped the outcome. Second question for the thread.
- **R4. Keep pairwise comparison** (main against the extending alt chain)
  instead of the multi-chain elimination. With two chains they are the same;
  a probe counts decisions with a third chain inside the window.

## Components

### D. Daemon (`patches/monero-sim-pop.patch`), log v4

- **D1 window.** In `sim_sop_should_switch`: count `n_alt'` over
  `alt_chain` minus its first block, and `n_main'` over main heights
  `hf+1..top` (patch `hf` is the first alt block, so spec h_f+1 = patch
  `hf`). Subjective iff online, `h0 + 1 < hf`, the existing difficulty gate,
  `max(n_alt', n_main') < (k-1)*w`, and fork depth `< 10*w`.
- **D2 nakamoto.** If `max(alt tip, top) - (hf - 1) >= 10*w`, compare plain
  cumulative difficulty. Replaces the per-block "older than 10*w from the
  tip" legacy weight. Our forks never get this deep; it is for conformance.
- **D3 tip shares in the objective score.** For each side, take the pooled
  shares with `prev_id` = that side's tip and `height` = tip + 1, keep the
  first-seen share per slot, count the contiguous run from `major_version`
  (R2), check PoW against `diff(tip+1)/w` (`sim_block_difficulty_at`, as
  for alt blocks), and add `unit` each when the regime is objective. Not
  counted in `n_alt'`/`n_main'`.
- **D4 alternate workshares.** `sim_add_workshare` rejects shares above the
  main chain height today (`height > get_current_blockchain_height()`).
  Admit a share whose parent is a known alt block at any height when that alt
  chain's fork point is within `10*w` of the main tip. Relay only shares that
  extend the main tip at admission (verify the current relay condition does
  exactly this). No retroactive relay after a switch (text is silent;
  recorded as an open point).
- **D5 log v4.** Per side: `n_obj` (above h_f+1), `tip` id, `pool`: every
  pooled share on that tip with `id`, `slot`, `seen`, `pow_ok`; and
  `pool_counted`. Top level: `nakamoto` flag, `v: 4`. Keeps all v3 fields
  except `nf`/`nf_main`/`nf_rule`, replaced by `n_alt`/`n_main`.
- **D6** No change to lateness, `ref_seen`, h0, tie draws, reinsert
  handling.

### O. Oracle (`scripts/sop_oracle.py`, `docs/20260930_sop_conformance.md`)

- Update the conformance doc from the current issue text first (new section
  "revised 2026-10-20", the old rules kept for v2/v3 records), then write
  `decide_v4()` from the doc, not from the patch.
- `check` dispatches on `v`; v3 records keep the current `decide()`.
- New `--pool-rule all` to recompute every v4 decision with every pool share
  counted (R2 alternative), reporting how many outcomes differ.

### A. Attacker (`agents/selfish_strategy.py`, `agents/selfish_miner.py`)

- **A1 window.** `_branch_weights` returns per-branch object counts without
  the first block; `window_stubborn` reveals once
  `max(att', hon') >= window_objects` (new default 32, the spec's
  `(k-1)*w`) and its weight beats honest's. Keep the old attacker-only test
  behind `window_rule: v3` so old specs reproduce.
- **A2 weigh with tip shares.** Honest weight adds the honest pool shares on
  the public tip (bridge `sim_get_workshares(prev_id=pub tip)`, counted as in
  R2); attacker weight adds its own miner's shares on its private tip (miner
  `sim_get_workshares(prev_id=priv tip)`), if A3 can deliver them.
- **A3 deliver its tip shares.** On a reveal: submit the blocks to the
  bridge, wait until the bridge's tip is the private tip, then submit the
  miner's tip shares to the bridge (`sim_submit_workshare`). They then extend
  the bridge's main tip and relay normally. Honest nodes that kept their
  chain receive them as alternate shares (D4).
- **A4** `deep_hunt` inherits A1-A3. Honest-share relay to the offline miner
  is unchanged.

### M. Race model (`scripts/sop_race_model.py`)

- `count_attacker_pending`: the attacker's tip shares count for it under the
  objective score (A3).
- A preset `--rule-version 20261020` = `either_window` +
  `count_honest_pending` + `count_attacker_pending`, used by `sweep`, `hunt`
  and `reconcile`. Check `count_honest_pending` is applied only past the
  window (it is, since wins are only checked there; add a test).

## Testing

- Strategy and miner: unit tests for A1 (first block excluded, either
  branch), A2 (weights with pool shares), A3 (share submission order and the
  wait on the bridge tip), `window_rule: v3` reproducing today's decisions.
- Oracle: hand-built v4 records, including one where the tip shares turn a
  SWITCH into a KEEP, one with duplicate slots (R2), one past `10*w`
  (nakamoto); v3 records still pass.
- Race model: preset tests; `as_run` rows unchanged.
- Daemon: owner compiles (`./setup.sh --sim-binary`, nothing running); then a
  12-daemon smoke, alpha 0.45 hs d5, 6 h: oracle 0 mismatches on all nodes;
  v4 records carry pool shares on both sides; the attacker's tip shares reach
  honest nodes after reveals (log grep); some objective decisions with a
  non-zero honest pool count.
- Probes on the smoke (R3, R4): share arrivals that would flip a decision;
  decisions with a third chain in the window.
