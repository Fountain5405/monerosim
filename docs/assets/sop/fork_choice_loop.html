What this shows

  1. Stock monerod already re-checks displaced blocks. After every reorg it pushes each one back through the fork-choice check. Under cumulative difficulty that check can never win, so nobody had to decide whether it should happen.
  2. Share-or-Perish's comparison can prefer each branch over the other. Its rules switch on n_f, which counts the side branch's work objects only, and they time blocks and workshares against whichever block is main at each height. Both depend on which branch the node is on.
  3. So the spec has to say what happens to displaced blocks, or use a comparison that gives the same answer whichever branch is main. The issue's two readings of n_f differ exactly here: the formal one counts the alt chain only (the cycle is possible), the prose one ("the two chains differ by fewer than k·w work objects") makes the pair objective once either side holds k·w (no cycle here). Options: judge each pair symmetrically, judge a displaced branch again only once extended (our simulator's default), or say a winning reveal is final until the loser is extended. We have not picked one.
  4. Revenue numbers from runs where monerod re-checked displaced blocks are not quoted: the attacker's blocks were deleted by an accident of monerod's re-insertion code (Act 2, step 9), not by any rule.
