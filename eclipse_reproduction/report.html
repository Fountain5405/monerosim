Reproduction study · Monero P2P security

Eclipsing an Unreachable Monero Node

Reproducing the Nyx eclipse attack against NAT'd Monero nodes in simulation — driving a firewalled victim's outbound connections onto attacker peers without ever contacting it directly.

Source paper: “Are Unreachable Nodes Truly Safe? Fully Eclipsing Monero's P2P Network!” Shi, Zeng, Lan, Zhang, Han, Luo, Jin, Du, Wang — ACM CCS 2026 (arXiv:2609.10260). Reproduced with monerosim v0.3.1 running real monerod v0.18.5.1 inside the Shadow network simulator.

✓

Core claim reproduced — full eclipse reached.

An unreachable, outbound-only Monero node can be driven into eclipse purely by poisoning the peerlists of reachable nodes and letting the protocol's own timed-sync and update_sync_search churn do the rest — no inbound connection to the victim is ever used. Against an established victim the takeover reached 11 of 12 outbound peers; against a newborn victim joining the poisoned network it reached the full 12 of 12 (100%) with a time-to-eclipse of ~31 minutes, close to the paper's ~27, thereafter oscillating between 11 and 12 as the paper itself reports. The victim's graylist ran 93–100% attacker records throughout. A same-config re-run reproduced the time-to-eclipse exactly.

The setup

What the attack does, and why simulation can test it

The victim is a node behind NAT or a firewall: it makes outbound connections but accepts none. It depends entirely on its outbound peers for discovery — so if those are captured, it has no protocol path back to the honest network.

Monerosim runs the real monerod daemon under Shadow, so the exact code the attack targets — the 1,000-slot whitelist, 5,000-slot graylist, the 12 outbound slots, the ~101-second update_sync_search refresh, and 60-second timed sync — is genuine, not a model. The victim is made unreachable deterministically: with reachable_fraction: 0.0 and a per-node reachable exemption on every other relay, Shadow drops inbound TCP to port 18080 on exactly one host — the target.

  1. Network-wide poisoning. Attacker-controlled reachable nodes fill honest nodes' whitelists with attacker records through ordinary handshakes and gossip.
  2. Peerlist infiltration. Honest nodes relay those records into the victim's graylist during routine timed sync — the only way records reach a NAT'd node.
  3. Connection takeover. The victim's own update_sync_search drops an outbound peer roughly every 101 s and refills it graylist-first — from the now attacker-dominated pool.

A control network with no attackers keeps the victim on honest peers for the whole run. Introduce an attacker-controlled majority of reachable nodes and the takeover unfolds exactly as the paper describes.

The py-levin injection primitive

Injecting arbitrary peer records into real monerod

The paper's efficient variant plants records with a lightweight Levin client rather than running full nodes. I implemented that client from the wire format up and verified it against a real daemon.

The injector speaks Monero's Levin framing and epee portable-storage payloads, presents the fakechain (mainnet) network_id, and answers a dialing daemon's handshake and timed-sync with a chosen local_peerlist_new. The load-bearing finding

Eclipse completeness scales with attacker endpoints

Both real-node and injector runs converge on the same rule: how eclipsed the victim gets tracks the number of distinct-/24 connectable attacker endpoints, not how many records you inject.

A victim's outbound slot is only captured when it makes a successful connection to a real attacker endpoint, and Monero's /24 diversity filter forces those 12 peers into 12 distinct /24 subnets. Injecting unreachable “trash” records evicts honest entries but cannot become connections — it dilutes the pool and lowers takeover. So the ceiling is set by how many genuine attacker endpoints exist across distinct /24s.

A 585-node run confirmed the poisoning at paper scale: with 550 attacker endpoints the victim's graylist ran 97.8% attacker (paper: ~97.1%) and honest whitelists were fully poisoned. Its takeover reached 9/12 and was still climbing when the 3-hour sim ended — at that size the takeover is rate-limited by update_sync_search (~one replacement every 101 s) against a trickle of honest records re-injected by the always-reachable seeds, so full convergence needs a longer run. The clean 12/12 above was instead reached the fast way — eclipse-at-birth: a newborn victim joining the poisoned network never establishes honest connections to displace, and reaches 12/12 in ~19 minutes of its lifetime. That path also reproduces the paper's second attack (Moros). Scaling it to the paper's size — a 963-node run with 951 attacker endpoints — the newborn victim was born fully eclipsed: on its first measurement it already held all 12 outbound slots on attacker nodes, with zero honest peers and zero inbound, and stayed a solid 12/12 across the entire 35-minute observation window with no oscillation. At ~950 endpoints the dose-response curve reaches its ceiling — the clean confirmation of the paper's ~1,000-subnet assumption.

Why this matters for the paper

The reproduction independently confirms that the attacker's control of ~1,000 /24 subnets is a load-bearing assumption, not a convenience — a point the accompanying manuscript review also flagged. The injection technique is what makes acquiring that many endpoints cheap on the real Internet; in a bounded simulation the endpoint count itself is the limit.

Honest differences

Scope and threats to validity

  • Scale. The paper ran 1,200 nodes; these runs range from ~10² up to a 963-node network — approaching the paper's size — bounded by Shadow's ~1,000-host scheduler cliff and a shared, memory-heavy host. Absolute timings still need not match the paper's ~27-minute time-to-eclipse; the mechanism, the trends, and the full 12/12 at paper scale are what reproduce.
  • Honest seeds & anchors. monerosim injects six real hardcoded seed nodes, always reachable. A persistent seed connection left the real-node run at 11/12 rather than 12/12 — consistent with the review's note on anchor/seed persistence.
  • /24 filter kept on. The paper disabled Monero's /24 outbound-diversity filter because its 1,000 IPs sat in few /24s. Here every attacker node lands in its own /24, so the stock filter stayed enabled — a more conservative setting.
  • Client version. monerosim pins v0.18.5.1; the paper measured v0.18.4.3. The review notes the attack is, if anything, marginally stronger on v0.18.5.x.
  • No mainnet. The paper's second attack (eclipse-at-birth) was run against controlled targets on Monero mainnet. This reproduction stays entirely in simulation.
  • Reproducibility. Shadow is deterministic in virtual time and every scenario pins a fixed seed; a same-config re-run of the eclipse-at-birth case reproduced the time-to-eclipse exactly (30.8 min). In steady state the takeover rate oscillates 11–12 as the last honest peer is repeatedly dropped and re-displaced.
